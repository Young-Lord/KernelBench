# 摩尔线程 MUSA 算子评测集构建指南（A / B 两级）

## 一 两级分类

按**解题方式**分成两级。这不是难度阶梯，而是两条能力轴：题目、允许调用的 API、基线、指标、审计口径、榜单全部独立。

|  | A 类：算子实现（`tier: "A_kernel"`） | B 类：库集成（`tier: "B_library"`） |
| --- | --- | --- |
| 题目本质 | 自己写 kernel 完成核心计算 | 选对库路径，并兜住库不支持的配置 |
| 能否调用 muDNN / muBLAS / SDPA / ATen | 禁止 | 允许，且是首选路径 |
| 库是否有等价实现 | 没有（是变体、融合，或库不覆盖） | 有，且覆盖大部分目标配置 |
| 难点 | tiling、在线 Softmax、shared memory、非对齐 shape | 能力探测、分派、降级路径、中间张量开销 |
| speedup 分母 | 上游 MUSA 实现（退化时用 muDNN 融合实现） | 维护者手写的 expert 分派 |
| 核心指标 | Compile Rate、Correctness、Speedup | 加 Coverage Rate、Fallback Correctness、Dispatch Efficiency、Expert-relative Speedup |
| 额外审计 | 库调用残留、CUDA 宏替换 | 分层检查、链接白名单、分派轨迹、CPU 计算、版本硬编码 |
| 榜单 | A 轨独立排名 | B 轨独立排名，**不与 A 轨合并或求平均** |

**判定规则**，按顺序问三个问题：

1. 库在目标 dtype / layout / shape 范围内，能否用一次调用给出完全相同的语义？能 → 候选 B 类；不能 → 候选 A 类。
2. （对候选 A）禁掉库之后还有可行的 kernel 实现吗？如果没有——它的语义就是某个库算子的等价物，自己写等于重写库——那它其实是 B 类题。
3. （对候选 B）隐藏配置里是否存在库不覆盖、或语义不等价的项，且朴素分解与 expert 分派之间有明显延迟差距？两者皆有 → B 类成立；任一不成立 → 这题没有区分度，退回重设计。

## 二 评测集包含什么

| 部分 | 内容 | 给 Agent | 存放位置 |
| --- | --- | --- | --- |
| 原始来源 | 仓库快照、Commit、LICENSE、原始实现与测试 | 否，仅溯源与专家基线 | `sources/<id>/` |
| 环境快照 | GPU、驱动、Toolkit、编译器、muDNN/muBLAS、torch_musa、编译参数、镜像 digest | 脱敏版可见 | 环境快照文件 |
| 公开任务 | 任务契约、语义契约、题面、reference、公开 Case、Starter 工程 | 是 | `tasks/<id>/` |
| 隐藏评测 | 隐藏 Case、golden、边界与极端 Case、性能 Case、泛化探针 | 否 | `private/<id>/` |
| 官方基线 | 四条参照基线；B 类另加朴素组合与 expert 分派 | 否 | `private/<id>/` |
| 评测器 | 编译、正确性、边界、稳定性、性能与审计脚本 | 评分口径可见，脚本不可见 | `evaluator/` |

不把上游源码、仓库名、Commit URL 交给 Agent。Agent 只依据语义契约与 reference 重新生成 kernel。

## 三 目录结构与 Starter 分工

```text
<eval_root>/
├── sources/<id>/       # 仅维护者：快照记录 + Commit + LICENSE（快照本体在库外）
├── tasks/<id>/         # Agent 可见：任务契约、语义契约、题面、reference、公开 Case
└── private/<id>/       # 仅评测端：隐藏 Case、golden、基线
```

公开目录只放任务定义，原始源码与隐藏资产必须与 Agent 隔离。

> **实现说明（2026-09-20）**：编译、正确性、计时、speedup 与源码审计均已改为复用
> KernelBench 框架（`src/kernelbench/` 下的 `eval.py`、`timing.py`、
> `kernel_static_checker.py`、`musa_extension.py`），因此不再需要独立的
> `evaluator/` 目录。同理，下面这份冻结 Starter（C++17 + 裸二进制 ABI）已经弃用：
> B 类必须经 torch_musa 调用 muDNN，"绕开 libtorch"与题目前提冲突。
> 被测程序统一交付 KernelBench 风格的 Python `ModelNew`，兜底 kernel 用
> `musa_extension.load_inline` JIT 编译 `.mu`。下表保留作为分工设计依据。

| Starter 内的文件 | 角色 | A 类 | B 类 |
| --- | --- | --- | --- |
| 构建脚本与 CMake | 唯一构建入口，链接白名单在此固定 | 只链 MUSA Runtime | 另链白名单库，白名单来自任务契约 |
| 公共头文件 | 类型别名、错误检查宏、启动/分派接口 | 冻结 | 冻结，另含路径枚举与轨迹接口 |
| 主程序 | 解析 Case 输入输出参数 | 冻结 | 冻结，另解析分派轨迹开关 |
| Host 启动 | grid / block / shared memory 配置 | 可改（仅标记区域） | 可改，另含库调用封装 |
| Device kernel | 核心计算 | 可改 | 可改，只写兜底 kernel |
| 分派文件 | 能力探测与形状分派 | 无 | 可改（仅标记区域） |
| 张量读写 | 裸二进制 + JSON manifest 的 IO | 冻结，与 B 类逐字节相同 | 冻结，与 A 类逐字节相同 |

## 四 配套文件各自要写什么

### 4.1 任务契约

面向评测器的机器可读定义，算子 id、family、容差、禁止项在此唯一声明，其他文件引用而不重复定义。

最少记录：tier、id、name、family、来源（仓库 / Commit / LICENSE / 快照位置）、目标环境（设备、架构、Toolkit）、输入与累加 dtype、layout、shape 范围与动态性、超参数、容差（atol、rtol、最大绝对误差）、禁止项、入口文件与可改文件清单、时间预算、必需与可选输出。

B 类额外记录四项：允许链接的库与允许调用的符号前缀、分派文件路径、必需的分派轨迹、库缺口配置的最少条数与必须覆盖的缺口原因。

禁止项里 A 类写"库前缀 + ATen + CUDA 残留"；B 类改成"白名单之外的库 + ATen + CUDA 残留 + Host 端 CPU 数学库 + 联网获取实现"。

### 4.2 语义契约

它的作用是让同一 family 的 A 题与 B 题可比。分级不影响本文件：若两份语义契约不一致，golden 与 Case 生成器就无法复用，两级成了两套不可比的评测。

最少记录：张量签名（各输入输出的形状、dtype、layout、stride）、动态轴的取值范围、ABI（张量文件格式、谁负责分配释放、用哪个 stream）、Softmax 语义（是否 max-shift、累加 dtype）、确定性要求与种子注入方式。

以下三项必须写死，含糊会让 golden 直接出错，而且从失败现象很难反推：

1. 因果 mask 的对齐方式。S_q == S_kv 时无歧义，交叉注意力下有两条不兼容的约定：top_left（query i 屏蔽 j > i，PyTorch SDPA）与 bottom_right（屏蔽 j > i + (S_kv - S_q)，FlashAttention）。必须显式声明并全程锁定，不得同题混用。
2. 窗口方向。window_size=(left, right) 表示 query i 可见 j ∈ [i-left, i+right]，-1 表示该方向不限。
3. "全 mask 行"约定。纯因果 + 窗口语义下每行至少能看到 j = i，不存在空行；全 mask 行只在显式 mask 或变长 padding 下出现，约定为输出 0、LSE 取 -inf。该约定仍要写进语义契约，它对 mask / varlen 系列是必需的。

### 4.3 Case 清单（公开一份、隐藏一份）

两份格式相同，仅内容与可见性不同。核心原则：清单只描述参数与 seed，不存张量；张量由生成器按 seed 确定性生成，golden 单独存放。

每个 Case 记录：case_id、tag、seed、dtype、形状、属性（scale、mask、窗口、GQA 比例等）、输入分布、容差、golden 路径。

tag 取固定枚举，便于分类统计：smoke、correctness、boundary、non_aligned、extreme、perf、generalization。性能 Case 另带预热次数、测量次数、重复轮数与统计量。

生成规则：公开 3~5 个 smoke（含 golden，供 Agent 自测）；隐藏覆盖正确性、边界（S 非 tile 对齐、D 非 2 的幂、H 非 4 的倍数、S_q != S_kv）、极值、性能；另加泛化探针——不在任何清单里的随机 shape，用来识别打表实现。公开与隐藏不共用 seed，shape 区间不重叠。

B 类每个 Case 另加两个字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 期望路径 | 融合库 / 库组合 / 自研兜底 | 维护者对正确分派的预期，与分派轨迹逐条核对 |
| 库缺口 | 空，或 {原因, 期望路径, 依据} | 原因取固定枚举：形状不支持 / 语义不等价 / layout 不匹配 / 需要多算子组合 |

两条 B 类专属纪律：

- 库缺口只出现在隐藏清单，且不得少于 3 条、原因至少覆盖两类；公开清单一律无缺口、期望路径一律是融合库。公开清单里出现缺口，等于把考点直接告诉 Agent。
- 用对象而非布尔值。固定的原因枚举让评测器能统计"哪一类缺口没被兜住"，自由文本做不到。

### 4.4 基线与评分口径

最少记录：机器指纹（与完整环境快照同源）、测量协议（预热次数、测量次数、重复轮数、中位数、事件计时、是否锁时钟）、各条基线在每个性能 Case 上的延迟分位数与吞吐、显存峰值、数值、状态，以及评分口径。

| 基线条目 | A 类 | B 类 |
| --- | --- | --- |
| 上游 MUSA 实现 | 必需，性能上界 | 必需 |
| muDNN 融合实现 | 必需，参照 | 必需 |
| torch_musa SDPA | 必需，参照 | 必需 |
| torch_musa eager | 必需，仅交叉验证语义 | 必需 |
| 朴素库组合 | — | 必需，作为下界 |
| expert 分派 | — | 必需，作为 speedup 分母 |

B 类评分口径：speedup 分母指向 expert 分派，参照系指向朴素组合，门禁是"隐藏正确性全过且分派轨迹全部匹配期望路径"。另记朴素组合与 expert 分派的实测延迟比值，低于 1.3 的题出题阶段淘汰。

基线必须与被测实现在同一机器、同一镜像、同一编译参数下测得，否则 speedup 无意义。

### 4.5 题面（Agent 可见的任务说明）

与任务契约的分工：后者面向评测器（严格、字段化），前者面向模型（可读、有提示、有陷阱提醒）。字段：目标、交付物、必须做、禁止做、工程提示、评分口径、尝试预算。

必须做 / 禁止做 在两级方向相反，写错比写漏更糟：

| 项 | A 类 | B 类 |
| --- | --- | --- |
| 必须做 | 三段核心计算全部在 Device kernel 内完成 | 优先走白名单内的库路径；库不覆盖的配置由自研 kernel 兜住；用运行时探测决定分派，不得按版本号硬编码 |
| 禁止做 | 调用 muDNN / muBLAS / SDPA / ATen | 白名单外调用任何库；把数据拷回 Host 计算；联网或动态加载取实现；把第三方 kernel 源码改名内联（调库可以，搬源码不行）；全局降级成朴素实现 |
| 评分口径 | Speedup = 上游基线 / 生成实现 | Speedup = expert 分派 / 生成实现，且分派轨迹必须匹配期望路径 |

工程提示里不得出现上游仓库名、具体 kernel 函数名、论文实现细节，只能给通用建议。B 类可以说明"库里存在什么能力类别"（例如"融合注意力算子通常只支持 head dim 到某个上限"），但不得写出具体函数名、版本号或参数组合。

### 4.6 Starter 工程清单

除工程本体外，还要有一份清单声明：可改与不可改文件、每个可改文件里允许填的标记位置、构建与运行命令、ABI、以及（B 类）链接白名单。评测器据此判断越界修改，并核对白名单与任务契约一致。

ABI 两级冻结且相同：从输入目录读张量清单与 .bin，跑 runner，向输出目录写张量清单与 .bin。张量用裸二进制加 JSON manifest 传递，runner 不引入 libtorch，避免把 ATen 带进被测进程。

两条 B 类专属约束：库调用只允许出现在分派文件与 Host 启动文件中，藏进 kernel 或张量读写会让静态审计失效；能力探测只能靠运行时返回值（形状、dtype、layout 是否接受，属性组合是否支持），不按版本号硬编码。

### 4.7 评测器

| 环节 | 作用 | 分级 |
| --- | --- | --- |
| 环境采集 | 产出完整环境快照与脱敏版 | 共用 |
| Case 生成 | 按清单与 seed 生成张量与 golden，确定性可复现 | 共用 |
| 构建 | 只走 Starter 的构建入口这一条路径 | 共用 |
| 静态审计 | 越界修改、禁用 API、Host 计算、打表、Device 源码内容 | 共用 |
| 链接白名单核对 | 读构建产物导出表，核对实际链接的库 | 仅 B |
| 分派轨迹核对 | 解析运行输出的分派记录，与期望路径逐条比对 | 仅 B |
| 正确性 | 隐藏正确性、边界、稳定性复跑 | 共用 |
| 性能 | 预热后重复计时，产出基线与样本 | 共用 |
| 汇总 | 按权重汇总，产出评测报告 | 共用 |

退出码统一（0 通过，非零为具体失败类别），任一环节失败即短路，不进入后续环节。

### 4.8 Schema 校验

任务契约、语义契约、Case 清单、基线、环境快照、评测报告各有一份 schema，全部带版本号；tier 是枚举，校验时按值放宽或收紧字段（A 类出现"允许库"即报错，B 类缺"库缺口"定义即报错）。所有配套内容入库前必须过校验——这是防止手写内容漂移的唯一低成本手段。

## 五 构建流程

| 步骤 | A 类 | B 类 |
| --- | --- | --- |
| 1 固定环境 | 记录设备、架构、驱动、Toolkit、编译器、编译参数、镜像 digest。编译参数要精确到架构与 fast-math 开关级别，它们直接影响可比性 | 同 A，另记录 muDNN / muBLAS 版本，评测前比对 |
| 2 保存来源 | 完整快照 + Commit + LICENSE + 原始实现与测试，只进来源目录 | 同 A，快照另作 expert 分派的写法参考 |
| 3 提取语义 | 写独立 reference（CPU fp64 分块实现）与语义契约，写死 4.2 的三项约定 | 完全复用 A 的 reference 与语义契约，同一 family 的 A/B 题必须同语义 |
| 4 定义任务 | 手写任务契约与题面 | 另加允许库、库缺口定义、轨迹要求；必须/禁止方向反转 |
| 5 生成测试 | 公开 smoke + 隐藏正确性 / 边界 / 极值 / 性能 + 泛化探针 | 再加库缺口隐藏 Case（≥3 条、≥2 类原因），公开清单不透露缺口 |
| 6 统一接口 | 用 A 类 Starter，可改 kernel 与 Host 启动 | 用 B 类 Starter，可改上述两个加分派文件，构建白名单来自任务契约 |
| 7 建立基线 | 测四条参照基线 | 另加朴素组合与 expert 分派，算延迟比值，低于 1.3 淘汰本题 |
| 8 接入评测器并切分 | 静态审计 → 编译 → 公开 → 隐藏 → 边界 → 稳定性 → 性能 | 编译后加白名单核对，隐藏后加缺口 Case 与分派轨迹核对。两级分别切分、分别排名 |
